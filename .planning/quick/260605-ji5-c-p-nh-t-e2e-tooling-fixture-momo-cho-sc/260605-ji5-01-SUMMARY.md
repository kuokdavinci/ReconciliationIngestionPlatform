## Sequential Test Instructions (E2E happy path)

Assumes MongoDB is reachable per `scratch/seed_momo_e2e.py`'s env defaults
(`MONGODB_URI`, `MONGODB_DB` from `src/config/settings.py`).

### Step 1 — Clean Phase 1 baseline

```bash
make momo-e2e-reset
```

This wipes all MOMO collections, seeds exactly 20 wave1 internal rows
(`MOMO_TXN_9000`..`MOMO_TXN_9019`), and writes a partner xlsx with the same
20 keys. The CLI also (re-)creates the MOMO `fetch_config` (FILEDROP →
`./sftp_data`).

**Expected after running the scheduler / ingest once:**
- 20 `MATCHED` records
- 0 `MISSING_PARTNER`

### Step 2 — Add Phase 2 (incremental wave)

```bash
make momo-e2e-phase2
```

This adds exactly 20 wave2 internal rows (`MOMO_TXN_9100`..`MOMO_TXN_9119`)
and **overwrites** the partner xlsx with the 20 wave2 keys. Wave1 internal
rows are left in place — the engine's `INCREMENTAL_APPEND` scope filter
(`src/reconciliation/engine.py:159-163`) is the thing that scopes them out.

**Expected after running the scheduler / ingest again:**
- 20 new `MATCHED` records (wave2 only)
- 0 `MISSING_PARTNER`
- No review packet creation (the approved config from Step 1 is reused)

### Step 3 — Missing-partner demo

```bash
make momo-e2e-reset
make momo-e2e-missing-partner-demo
```

`reset` establishes the 20 wave1 baseline. `missing_partner_demo` adds the
single `MOMO_TXN_90_MISSING_PARTNER` internal row (50000 VND, `SUCCESS`,
same day) and writes a wave1-only partner xlsx. **Important:** the next
ingestion must be a `FULL_SNAPSHOT` (i.e. no `source_file_id` passed to
`ReconciliationEngine.reconcile`) — that's what makes the engine see all 21
internal rows and flag the missing one.

**Expected after a FULL_SNAPSHOT ingestion:**
- 20 `MATCHED` records
- 1 `MISSING_PARTNER` record whose `partner_txn_id` is `MOMO_TXN_90_MISSING_PARTNER`

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `Decimal` → `Decimal128` for production pymongo serialization**

- **Found during:** task 1, writing the testable `_build_internal_doc` helper
- **Issue:** The original `_seed_internal` went through `InternalTransactionRepository.create(tx)`, which internally calls `_prepare_for_mongo` (`src/models/repository.py:39-47`) to convert `Decimal` → `Decimal128` before insert. The refactored helpers use `db["internal_transaction"].insert_one(doc)` directly, so the Decimal→Decimal128 conversion had to happen at the doc-construction layer.
- **Fix:** `_build_internal_doc` now wraps `amount` in `bson.decimal128.Decimal128(str(amount))` so the doc is pymongo-serializable in production. Tests with mocks see Decimal128 in `insert_one.call_args_list` but don't assert on the amount, so test simplicity is preserved.
- **Files modified:** `scratch/seed_momo_e2e.py`
- **Commit:** `4ece2b1`

**2. [Rule 1 - Bug] Conftest `mock_db` returns fresh MagicMock per `__getitem__` call**

- **Found during:** task 3, first pytest run failed with `TypeError: 'MagicMock' object can't be awaited`
- **Issue:** The conftest fixture `mock_db` uses `db.__getitem__ = MagicMock(side_effect=lambda name: MagicMock())`, which creates a **new** MagicMock on every `db[name]` access. The initial test setup that wired `AsyncMock` onto `mock_db["internal_transaction"]` was therefore lost by the time the helper did its own `db["internal_transaction"]` lookup.
- **Fix:** The `_setup_internal_collection` test helper now creates a single collection MagicMock and **overrides** `mock_db.__getitem__` to return it consistently. All `db[...]` accesses in the helper see the same mock.
- **Files modified:** `tests/test_seed_momo_e2e.py`
- **Commit:** `f0d15b9`
