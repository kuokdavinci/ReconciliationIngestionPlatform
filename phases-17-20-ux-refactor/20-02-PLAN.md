# Plan 20-02: Contextual Copilot per Screen

## Goal

Copilot context varies by screen. Backend accepts `screen` param (intake/review/reconciliation/automation), returns tailored context. Frontend passes screen when fetching copilot context.

## Tasks

### Task 1: Backend — add `screen` param to context endpoint

In `src/api/copilot.py`:
- Add `screen: str = Query("intake")` to `get_context`
- Pass `screen` to `CopilotContextService.context()`

In `src/services/copilot_context.py`:
- `resolve()` accepts `screen` param
- Adjust `_headline`, `_summary`, `_reasons`, `_actions` to return screen-relevant content
- For `intake`: status, latest file issues, pending changes (current behavior)
- For `review`: pending count, risk summary, recommendation
- For `reconciliation`: anomaly count, matched %, top patterns
- For `automation`: last failure reason, error context, retry suggestion

### Task 2: Frontend — pass screen per route

In `render()` for each route:
- Data Intake: `screen=intake`
- Review Center: `screen=review`
- Reconciliation: `screen=reconciliation`
- Automation: `screen=automation`

Update the copilot context fetch URL to include `&screen=...`.

### Task 3: Ensure no stale context between screens

When route changes, `state.copilotContext` is refreshed by the async render fetch. Verify context isn't shared between different route renders.
